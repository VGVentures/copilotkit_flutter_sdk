# Implementation Plan: `json_serializable` for JSON (de)serialization

Branch: `chore/json-serializable` (worktree `../copilotkit-json-serializable`). Tasks: `tasks/json_serializable/todo.md`.
The Phase 1 SDK plan in `tasks/plan.md` / `tasks/todo.md` is separate work and is not touched here.

## Overview

Replace hand-written `jsonEncode` / `jsonDecode` + `as` casts on fixed-shape payloads with typed models generated by `json_serializable` (`json_annotation` at runtime, `build_runner` + `json_serializable` as dev dependencies). The goal is readability and type safety at the JSON boundary; behaviour stays the same. Both `example/` and the core package (`copilotkit`) are in scope. Rollout starts in `example/` (no published API impact) so the toolchain is proven before core takes on `json_annotation` as a runtime dependency.

## Current JSON usage (audit, Oct 14)

| Location | Shape | Fit |
| --- | --- | --- |
| `example/lib/demo/weather_demo.dart`: `lookUpWeather` args (`args['city'] as String?`) and result (`jsonEncode({city, temperatureC, condition})`); `WeatherCard._decode` (`jsonDecode` + map casts) | Fixed | **Good**: Phase 1 |
| `packages/copilotkit/lib/src/transport/ag_ui_transport.dart` `stop()`: body `{runId}`; runtime replies `{stopped, interrupt?}` (currently ignored) | Fixed | Fair: Phase 2 |
| `JsonSchema` (`tools.dart`) | Variable (schema builder) | No: leave as is |
| AG-UI events / messages (`ag_ui`) | Owned upstream, has its own `toJson`/`fromJson` | No |
| `partial_json.dart`, `json_patch.dart`, `CopilotContext` values, `jsonEncode(entry.value)` in `client.dart` | Arbitrary JSON | No |

## Architecture Decisions

- **Example first, then core.** `example/` is a closed app, so codegen there carries no API risk and proves the toolchain. Core follows in Phase 2 (confirmed Oct 14); `json_annotation` becomes a runtime dependency of `copilotkit`, and models stay internal (not exported).
- **Generated `*.g.dart` files are committed.** This is VGV convention: CI and new engineers don't need a `build_runner` step to analyze or test, and the demo device setup (I3 onboarding target under 15 min) stays unchanged. CI checks that the committed output is up to date.
- **Package-level `build.yaml`** with shared options (`explicit_to_json: true`, `include_if_null: false`, `checked: true`, `disallow_unrecognized_keys: false`) so models stay small and consistent.
- **Generated code is excluded from analysis and coverage** (`analyzer.exclude: '**/*.g.dart'`; `coverage_excludes: '**/*.g.dart'` in `very_good_workflows`, `--exclude-coverage '**/*.g.dart'` locally). Models are still covered by round-trip tests on their hand-written parts.
- **Models are plain immutable classes** (`@JsonSerializable()` + `factory .fromJson` / `toJson`), using the repo's Dart 3.13 constructor syntax if the generator supports it (verified in Task 1), otherwise classic constructors in model files only.
- **Tolerant decoding stays tolerant.** Where the current code falls back on bad input (e.g. `WeatherCard` shows the raw string), the model wrapper catches `CheckedFromJsonException` / `FormatException` and keeps that fallback.

## Risks and Mitigations

| Risk | Impact | Mitigation |
| --- | --- | --- |
| `json_serializable` / `source_gen` don't resolve with `analyzer` 13.x, the Dart 3.13 SDK, or `flutter_test`'s `test_api` pin in the workspace | High: blocks everything | Task 1 is a spike; if it fails, record the blocker and stop before touching real code |
| Generator doesn't understand `const new(...)` / private named params | Med | Model files use classic constructor syntax; document the exception in Task 1 |
| Committed `*.g.dart` drifts from sources | Med | CI step: `build_runner build` then `git diff --exit-code` |
| Behaviour change in tolerant parsing (weather card fallback, stop reply) | Med | Tests for malformed input written before the switch |
| `json_annotation` becomes a runtime dependency of the published core | Low/Med | Accepted (small, stable package); models kept internal so the public API doesn't expose generated code |
