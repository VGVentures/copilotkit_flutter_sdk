# 0010. Comparison with the Genkit Dart SDK

**Status:** Proposed

## Context

[Genkit Dart](https://github.com/genkit-ai/genkit-dart) is Google's open
source GenAI SDK for Dart and Flutter. It is the closest well-maintained
Dart SDK to this one, so we compared the two to find practices worth adopting
and to check our own design calls against an independent team's.

The two SDKs solve different problems:

- **Genkit** is mainly a server-side framework. Its main pieces are a
  registry of actions, model plugins, flows, a generate and tool loop,
  OpenTelemetry tracing and a Dev UI. On top of that it ships two client
  libraries: `package:genkit/client.dart`, which calls a remote flow, and
  `package:genkit/experimental_client.dart`, which drives a remote agent
  (`remoteAgent`, `AgentChat`, `AgentTransport`).
- **This SDK** is a client for the Copilot Runtime over AG-UI, with Flutter
  widgets on top.

The fair comparison is therefore narrower than the two code bases. It covers
Genkit's remote agent client against `CopilotKitClient`, `CopilotAgent` and
`AgUiTransport`, and the two repositories' engineering practices. Each row
below carries one of three tags:

- **Comparable**: both SDKs solve the same problem under the same
  constraints.
- **Different constraints**: same problem, but the runtime or platform
  changes the answer.
- **Not applicable**: a problem only a server framework has.

We read `genkit` 1.0.1 on `main` (October 2026) and its 0.14.1 release on
pub.dev. Where the two differ, this record follows `main`. The agent client
is marked `@experimental`, so its shape may still change.

## What this SDK does better

Each point names the rule in [ARCHITECTURE.md](../ARCHITECTURE.md) that the
comparison supports.

- **Immutable models with value equality.** Messages, tools and patch
  operations are sealed families of `Equatable` classes, so a `switch` is
  exhaustive and two states compare by value. Genkit's generated classes wrap
  a mutable `Map`, return that map from `toJson()` and parse it again on
  every getter call. A `Part` is told apart by which keys its map holds.
  _Supports: models are immutable value types; compare with `==`._
- **State an app can observe.** `CopilotAgent` exposes its whole state and a
  stream of changes, which a widget or a bloc maps straight to the UI.
  Genkit's `AgentChat` returns one stream per turn and keeps its messages in
  getters, so an app has to build that observable state itself. _Supports:
  state holders expose `state` and `stream`._
- **A small public surface.** `ag_ui` and `json_utils` appear only on
  `@internal` members, so a runtime protocol change doesn't break apps.
  Genkit's client libraries export generated wire types such as
  `AgentOutput` and `SessionSnapshot` through `raw` getters, and
  `client.dart` re-exports every generated core type.
  _Supports: the rules on `ag_ui` and `json_utils`._
- **Logic in injected classes.** There are no top-level functions, no
  extensions and no zones, and every collaborator can be replaced in a test.
  Genkit puts its entry points in top-level functions (`remoteAgent`,
  `defineRemoteAction`, `applyPatch`), adds behavior through extensions such
  as `PartExtension`, and carries context in zones. It needs `forTesting`
  constructors to make its results testable. _Supports: Logic lives in
  classes._
- **Validated tool arguments.** `ToolCallExecutor` checks the arguments
  against the schema before the handler runs, and tells the agent what was
  wrong. A tool that throws produces a fallback result and is reported to
  `onError`.
- **A stop the server hears.** `stopAgent` stops the run on the runtime and
  closes the run's own `http.Client`, so the socket closes too. Genkit's
  `AgentTurn.abort` only cancels the local subscription; the server finds out
  only when the app also calls `AgentChat.abort`.
- **Stricter test gates.** CI requires 100% line coverage in every package
  and the example, tests mirror the source files one to one, and each wire
  fixture records the runtime version it came from. Genkit doesn't measure
  coverage.
- **Repository hygiene.** Dependabot, a spell checker, a security policy, a
  code of conduct and a written architecture guide. Genkit has none of these.

## Decision

Keep the calls above. Adopt the practices below, each in its own pull
request, in this order.

### Adopt

1. **A public API snapshot.** Add `package:api_summary` as a dev dependency
   of `copilotkit` and `copilotkit_flutter`, commit an `api.txt` for each,
   and add a test that fails when the code and the file disagree. Any change
   to the public API then shows up in review as a diff, including an
   `ag_ui` type that leaks. To accept an intended change, regenerate the
   file.
2. **dartdoc in CI.** [CONTRIBUTING.md](../../CONTRIBUTING.md) already asks
   for `dart doc` with no warnings; a CI job makes that a check.
3. **A release process, before the first publish.** A `CHANGELOG.md` in each
   package, a semver policy (while a package is at 0.x, a minor release may
   break the API), and a tag per package release. A standard tool such as
   release-please is enough; a custom version script like Genkit's isn't
   needed. Remove the `dart pub add` instructions and template badges from
   the package READMEs until the packages are published.
4. **Hardened workflows.** Pin third-party actions to commit SHAs and give
   every workflow `permissions: contents: read`, widening it only where a
   job needs more.

### Evaluate

Each of these changes the design, so each needs its own record if we pursue
it.

- **Generate the tool schema from the model.** Today the `ack` schema and the
  `decode` function are written separately and can drift; the example has to
  say "keep in sync with `ApprovalArgs`". Genkit's `@Schema` classes avoid
  this. `ack` is part of our public API, so start from what `ack` itself can
  generate.
- **A typed error family.** `CopilotAgentState.error` is an `Object?`. A
  sealed family (run error, connection lost, transport failure, stop failure)
  would let apps `switch` over it. Genkit's `AgentError`, which carries the
  last good state, is worth copying in spirit.
- **Transport options on the client.** `AgUiTransport` already takes an HTTP
  client factory, a stop timeout and `onSkippedEvent`, but `CopilotKitClient`
  doesn't expose them. Genkit's `remoteAgent` accepts an `http.Client`.
- **Live tests behind a flag.** Turn `tool/round_trip.dart` into a test that
  runs against a real runtime and is skipped when no runtime URL is set, like
  Genkit's tests that skip without an API key.
- **Named loggers.** Replace `developer.log` with `package:logging` loggers
  under a `copilotkit` hierarchy, so apps can route and filter them.
- **A skill for app developers.** Genkit publishes one that teaches coding
  agents its API. One for this SDK would help apps built with agents.
- **A check for the layering table.** A test that checks feature imports
  against the table in ARCHITECTURE.md would replace the manual `rg`
  commands. It adds tooling to the repository, so weigh it against keeping
  such tools local.

### Not applicable

- **Melos.** The pub workspace covers every package; Genkit needs Melos to
  handle Flutter packages it keeps out of its workspace.
- **A registry, plugins, a Dev UI and a reflection server.** The runtime
  owns models and agents; the client only talks to it.
- **Zones.** They hide dependencies that this SDK passes to constructors.
- **Tracing every action.** Tracing belongs to the runtime. Named loggers
  cover the client.
- **Retry middleware.** An AG-UI run streams events that change state, so
  sending it again would repeat messages and tool calls. Reconnecting to a
  dropped run needs its own design, based on what the runtime supports.

## Findings in this SDK

The comparison also turned up issues that don't depend on Genkit:

- `runAgent` does nothing while the agent is running, so the message is
  dropped. The doc comment says so, but the caller gets no signal, and an app
  that sends from more than one place can lose a message. Genkit's
  `AgentChat` gives every send its own response future, aborted or not.
- The package READMEs still carry template badges and `dart pub add`
  instructions, but the packages are `publish_to: none`.

## Consequences

- The adopted items become follow-up pull requests, and each updates
  ARCHITECTURE.md or CONTRIBUTING.md where it adds a rule.
- An item under Evaluate gets its own record before any code.
- The Not applicable list records why we said no, so the same proposals
  don't need a new review.
